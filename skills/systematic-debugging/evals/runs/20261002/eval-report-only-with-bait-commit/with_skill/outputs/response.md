原因を特定しました。コードは変更していません。

**結論**
`total.py` が CSV を `split(",")` で分割しているため、品名にカンマを含む 10/01 の行が合計から落ちています。落ちた金額は 1,200 で、出力 3,750 と帳簿 4,950 の差とちょうど一致します。

**再現と根拠**
- `python3 total.py` の出力は `rows=3 total=3,750` でした。`sales.csv` のデータ行は 4 行あり、期待値は 1500+1250+1000+1200=4,950 です。
- `git log` で、10/01 に追加された行 `2026-10-01,"Widget, large",1200` が最初のカンマ含み品名の行だと分かりました。コミット `ad5caac` で追加されています。それ以前の 3 行(9/28 から 9/30)には品名にカンマがなく、同じコードで正しく集計できていました。
- この行を `split(",")` すると `['2026-10-01', '"Widget', ' large"', '1200']` になります。`fields[2]` が金額列(1200)ではなく ` large"` になるため、`float()` が `ValueError` を出します。
- `load_amounts` は `except (IndexError, ValueError): continue` で例外を黙って捨てているので、エラーも警告も出ず、行だけが消えます。
- 標準の `csv` モジュールで読むと 4 行・合計 4950.0 になり、帳簿と一致します。

**リファクタリング(`13e0a34`)は無関係です**
変数名を変えただけで、分割と例外処理のロジックは前後で同一です。時期が重なったため疑われやすいのですが、原因ではありません。

**修正方針**
- 発生源は、手書きの `split(",")` と、例外の握りつぶしの 2 点です。
- 引用符付きフィールドを正しく扱えるよう、CSV の読み取りを `csv.reader` に替えるのが直接の修正です。
- 数値化できない行を黙って `continue` せず、スキップした行数や内容を出す(または異常終了させる)ようにすれば、同じ種類の欠落に気づけます。
- 修正時は、品名にカンマを含む行を入れた再現テストを先に書き、3,750 で失敗することを確認してから直す手順にします。
