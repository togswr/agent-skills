## Chapter 6: 基本リファクタリング

### Extract Function（関数の抽出）

- **目的**: コードの断片を理解し、その目的に基づいて名前を付けた関数に抽出
- **適用シナリオ**: コードの意図を理解するのに時間がかかる場合。6行以上は検討対象
- **手順**:
  1. 新しい関数を作成し、目的に基づいて名前を付ける
  2. 抽出したいコードを新しい関数にコピー
  3. 参照される変数をパラメータまたはローカル変数として調整
  4. 元のコードを関数呼び出しに置き換える
  5. テストを実行

### Inline Function（関数のインライン化）

- **目的**: 関数本体が名前と同じくらい明確な場合、関数を削除してインライン化
- **適用シナリオ**: 過度の間接化により読みづらくなっている場合
- **手順**:
  1. 関数がポリモーフィックでないことを確認
  2. すべての呼び出し元を見つける
  3. 各呼び出しを関数本体に置き換える
  4. 元の関数を削除

### Extract Variable（変数の抽出）

- **目的**: 式に名前を付けて理解しやすくする
- **適用シナリオ**: 複雑な式を分解して理解しやすくする場合
- **手順**:
  1. 抽出する式に副作用がないことを確認
  2. 変更不可の変数を宣言し、式のコピーを代入
  3. 元の式を新しい変数に置き換える
  4. テストを実行

### Inline Variable（変数のインライン化）

- **目的**: 変数名が式自体よりも説明的でない場合に削除
- **適用シナリオ**: 変数がリファクタリングを妨げている場合
- **手順**:
  1. 代入の右辺に副作用がないことを確認
  2. 変数への参照をすべて式に置き換える
  3. テストを実行

### Change Function Declaration（関数宣言の変更）

- **目的**: 関数名の変更、パラメータの追加・削除
- **適用シナリオ**: より良い名前を思いついた場合、パラメータリストを整理する場合
- **手順**:
  1. パラメータを削除する場合、参照がないことを確認
  2. 関数本体を変更
  3. すべての呼び出し元を更新
  4. テストを実行

### Encapsulate Variable（変数のカプセル化）

- **目的**: データへの直接アクセスをgetter/setter関数経由に変更
- **適用シナリオ**: データの参照と更新を制御したい場合
- **手順**:
  1. カプセル化する変数への参照・更新関数を作成
  2. すべての参照を関数呼び出しに変更
  3. 変数の可視性を制限
  4. テストを実行

### Rename Variable（変数名の変更）

- **目的**: より適切な名前に変更して理解しやすくする
- **適用シナリオ**: 変数の役割がより明確になる名前がある場合
- **手順**:
  1. 広くアクセスされる変数の場合、Encapsulate Variableを検討
  2. すべての参照を新しい名前に変更
  3. テストを実行

### Introduce Parameter Object（パラメータオブジェクトの導入）

- **目的**: 繰り返し出現するパラメータグループをオブジェクトに置き換える
- **適用シナリオ**: 同じパラメータセットが複数のメソッドに出現する場合
- **手順**:
  1. パラメータを保持する新しいクラスを作成
  2. メソッドにパラメータオブジェクトを受け取るパラメータを追加
  3. 古いパラメータを削除し、パラメータオブジェクトのフィールドに置き換え
  4. 関連ロジックをパラメータオブジェクトに移動することを検討

### Combine Functions into Class（関数群のクラスへの統合）

- **目的**: 共通のデータを繰り返し引数として渡す関数群を、そのデータを保持するクラスにまとめる
- **適用シナリオ**: 複数の関数が同じデータセットを受け取って処理している場合
- **手順**:
  1. 共通データを保持する新しいクラスを作成
  2. 共通データをコンストラクタで受け取りフィールドに格納
  3. 各関数をクラスのメソッドに移動し、共通データの引数を削除
  4. 呼び出し元をクラスのインスタンス化とメソッド呼び出しに変更
  5. テストを実行

### Combine Functions into Transform（関数群の変換関数への統合）

- **目的**: 元データから派生データを計算する関数群を1つの変換関数にまとめ、派生データの計算ロジックを一箇所に集約する
- **適用シナリオ**: 派生データの計算が複数箇所に散在している場合。不変データに適する（可変データにはCombine Functions into Classを推奨）
- **手順**:
  1. 元データを受け取り、そのディープコピーを返す変換関数を作成
  2. 派生データの計算を変換関数内に移動し、結果をコピーに付加
  3. 各計算について同様に繰り返す
  4. 呼び出し元を変換関数の使用に変更
  5. テストを実行

### Split Phase（フェーズの分割）

- **目的**: 異なる関心事を扱うコードを順次的なフェーズに分割し、各フェーズが独立した責務を持つようにする
- **適用シナリオ**: 1つの関数やモジュールが入力の解析と処理など、異なる段階の処理を混在させている場合
- **手順**:
  1. 第2フェーズのコードをExtract Functionで抽出
  2. フェーズ間で受け渡すデータを中間データ構造として定義
  3. 第1フェーズの出力を中間データ構造に格納
  4. 第2フェーズが中間データ構造のみを使用するよう調整
  5. テストを実行

## Chapter 7: カプセル化

### Encapsulate Record（レコードのカプセル化）

- **目的**: データ構造を隠蔽し、アクセスを制御
- **適用シナリオ**: 可変データ構造を直接公開している場合
- **手順**:
  1. レコードを保持するクラスを作成
  2. レコードを返すメソッドを追加
  3. すべての参照を新しいメソッド経由に変更
  4. レコードへのアクセスをカプセル化

### Encapsulate Collection（コレクションのカプセル化）

- **目的**: コレクションへの直接アクセスを防ぎ、コピーを返す
- **適用シナリオ**: コレクションを直接返すgetterがある場合
- **手順**:
  1. コレクションのコピーを返すメソッドを作成
  2. 要素の追加・削除メソッドを提供
  3. 直接アクセスを新しいメソッドに置き換え

### Replace Primitive with Object（プリミティブからオブジェクトへ）

- **目的**: プリミティブ型を意味のあるドメインオブジェクトに置き換える
- **適用シナリオ**: 電話番号、金額、座標などをプリミティブで扱っている場合
- **手順**:
  1. Encapsulate Variableを適用
  2. 新しい適切な名前のクラスを作成
  3. フィールドを新しいクラスのインスタンスに変更
  4. 関連するロジックを新しいクラスに移動

### Replace Temp with Query（一時変数をクエリに置き換え）

- **目的**: 一時変数を計算を行うメソッドに置き換える
- **適用シナリオ**: 一時変数が多くてExtract Functionが困難な場合
- **手順**:
  1. 一時変数が1回だけ代入され、副作用がないことを確認
  2. 式を返すメソッドを抽出
  3. 一時変数への参照をメソッド呼び出しに置き換え

### Extract Class（クラスの抽出）

- **目的**: 1つのクラスが2つの責任を持っている場合に分割
- **適用シナリオ**: クラスが大きすぎる、または複数の責任を持っている場合
- **手順**:
  1. 責任の分割方法を決定
  2. 新しいクラスを作成
  3. 元のクラスとの関係を作成
  4. Move FieldとMove Methodで機能を移動

### Inline Class（クラスのインライン化）

- **目的**: ほとんど何もしないクラスを削除
- **適用シナリオ**: Extract Classをやりすぎた場合、クラスの責任が減った場合
- **手順**:
  1. インライン先のクラスに機能を移動
  2. すべての参照を更新
  3. 元のクラスを削除

### Hide Delegate（委譲の隠蔽）

- **目的**: デリゲートオブジェクトへのアクセスを隠蔽
- **適用シナリオ**: `person.department.manager` のような連鎖呼び出しがある場合
- **手順**:
  1. デリゲートの各メソッドに対応する委譲メソッドを作成
  2. クライアントを新しいメソッド使用に変更
  3. デリゲートへのアクセサを削除

### Remove Middle Man（中間者の削除）

- **目的**: 過度な委譲メソッドを削除
- **適用シナリオ**: クラスが単なる委譲しかしていない場合
- **手順**:
  1. デリゲートオブジェクトへのアクセサを作成
  2. 委譲メソッドを削除し、クライアントを直接呼び出しに変更

## Chapter 8: 機能の移動

### Move Function（関数の移動）

- **目的**: 関数をより適切なコンテキストに移動
- **適用シナリオ**: 関数が別のクラスのデータをより多く使用している場合
- **手順**:
  1. 移動先のコンテキストで新しい関数を作成
  2. 元の関数から新しい関数にコードをコピー
  3. 元の関数を新しい関数への委譲に変更
  4. すべての参照を更新

### Move Field（フィールドの移動）

- **目的**: フィールドをより適切なコンテキストに移動
- **適用シナリオ**: フィールドがそれを使用するメソッドと同じ場所にない場合
- **手順**:
  1. 移動先にフィールドを作成
  2. フィールドへの参照をすべて移動先への参照に変更
  3. 元のフィールドを削除

### Move Statements into Function（文の関数内への移動）

- **目的**: 特定の関数呼び出しの前後で常に実行される文を、その関数の内部に移動する
- **適用シナリオ**: ある関数の呼び出し箇所で毎回同じ前処理・後処理が繰り返されている場合
- **手順**:
  1. 繰り返される文が全呼び出し箇所で同一であることを確認
  2. 対象の文を関数本体の先頭または末尾に移動
  3. 各呼び出し箇所から重複する文を削除
  4. テストを実行

### Move Statements to Callers（文の呼び出し側への移動）

- **目的**: 関数内の一部の文が呼び出し元ごとに異なる振る舞いを必要とする場合に、その文を呼び出し側へ移動する
- **適用シナリオ**: 関数の責務が広がり、一部の呼び出し元では異なる処理が必要になった場合。Move Statements into Functionの逆操作
- **手順**:
  1. 移動対象の文を特定
  2. 対象の文を各呼び出し元にコピー
  3. 関数本体から対象の文を削除
  4. テストを実行

### Replace Inline Code with Function Call（インラインコードの関数呼び出しへの置換）

- **目的**: 既存の関数と同じことをしているインラインコードを、その関数の呼び出しに置き換える
- **適用シナリオ**: ライブラリ関数やユーティリティ関数と同じロジックが手書きされている場合
- **手順**:
  1. インラインコードと同じ動作をする既存の関数を特定
  2. インラインコードを関数呼び出しに置き換える
  3. テストを実行

### Slide Statements（文のスライド）

- **目的**: 関連する文をまとめて配置
- **適用シナリオ**: 関連するコードが離れた場所にある場合、Extract Functionの準備
- **手順**:
  1. 移動したい文を特定
  2. 文が依存する要素の宣言より上には移動できないことを確認
  3. 参照される要素より下には移動できないことを確認
  4. 文を目的の場所に移動

### Split Loop（ループの分割）

- **目的**: 複数のことを行うループを1つずつ行う複数のループに分割
- **適用シナリオ**: ループが複数の処理を同時に行っている場合
- **手順**:
  1. ループをコピー
  2. 各ループで不要な部分を削除
  3. テストを実行
  4. パフォーマンスが重要な場合のみ後で結合を検討

### Replace Loop with Pipeline（ループをパイプラインに置き換え）

- **目的**: ループをfilter、map、reduceなどのコレクション操作に置き換え
- **適用シナリオ**: より宣言的で読みやすいコードにしたい場合
- **手順**:
  1. ループが作成するコレクションを特定
  2. filter、map、reduceなどのパイプライン操作で置き換え
  3. テストを実行

### Remove Dead Code（デッドコードの削除）

- **目的**: 使われていないコードを削除し、コードベースの理解を容易にする
- **適用シナリオ**: 呼び出されない関数、到達不能なコード、使用されない変数がある場合
- **手順**:
  1. コードが本当に使用されていないことを確認（参照検索）
  2. 対象のコードを削除
  3. テストを実行

## Chapter 9: データの再編成

### Split Variable（変数の分割）

- **目的**: 複数回代入される変数を別々の変数に分割
- **適用シナリオ**: ループ変数やコレクタ以外で複数回代入される変数がある場合
- **手順**:
  1. 変数宣言と最初の代入時に新しい名前に変更
  2. 2回目の代入の前に新しい変数を宣言
  3. 各代入ごとにこれを繰り返す

### Rename Field（フィールド名の変更）

- **目的**: フィールド名をより適切なものに変更
- **適用シナリオ**: フィールドの意味がより明確になる名前がある場合
- **手順**:
  1. Encapsulate Recordを適用
  2. フィールド名を変更
  3. すべての参照を更新

### Replace Derived Variable with Query（派生変数のクエリへの置換）

- **目的**: 他のデータから常に計算可能な変数を削除し、計算メソッドに置き換える
- **適用シナリオ**: 変数の値が他のフィールドから導出可能で、更新漏れによる不整合リスクがある場合
- **手順**:
  1. 派生変数へのすべての代入箇所を特定
  2. 値を計算するメソッドを作成
  3. 変数の読み取りをすべてメソッド呼び出しに置換
  4. 変数の代入と宣言を削除
  5. テストを実行

### Change Reference to Value（参照から値への変更）

- **目的**: 内部オブジェクトを不変の値オブジェクトとして扱い、変更時はインスタンスを丸ごと置き換える
- **適用シナリオ**: 内部オブジェクトが複数のオーナー間で共有される必要がなく、不変性により推論を単純化したい場合
- **手順**:
  1. 内部オブジェクトが共有されていないことを確認
  2. 内部オブジェクトのフィールドを不変にする（setterを除去）
  3. 値ベースの等価性チェックを実装
  4. 内部オブジェクトの変更をインスタンスの置き換えに変更
  5. テストを実行

### Change Value to Reference（値から参照への変更）

- **目的**: 同一エンティティの独立した複数コピーを、リポジトリから取得する共有参照に統合する
- **適用シナリオ**: 同じ論理エンティティを表すオブジェクトが独立して存在し、更新の同期が必要な場合。Change Reference to Valueの逆操作
- **手順**:
  1. 正規インスタンスを保持するリポジトリ（マップ/キャッシュ）を作成
  2. コンストラクタまたはファクトリが指定キーの既存インスタンスを返すようにする
  3. 直接のインスタンス化をリポジトリ経由の取得に置き換える
  4. テストを実行

## Chapter 10: 条件記述の簡略化

### Decompose Conditional（条件分岐の分解）

- **目的**: 複雑な条件分岐を名前付きメソッドに抽出
- **適用シナリオ**: 条件部分、then部分、else部分が複雑な場合
- **手順**:
  1. 条件部分をExtract Functionで抽出
  2. then部分をExtract Functionで抽出
  3. else部分をExtract Functionで抽出

### Consolidate Conditional Expression（条件式の統合）

- **目的**: 同じ結果を返す複数の条件を1つにまとめる
- **適用シナリオ**: 連続する条件チェックが同じアクションを実行する場合
- **手順**:
  1. 条件に副作用がないことを確認
  2. 条件をandまたはorで結合
  3. Extract Functionで条件を抽出して名前を付ける

### Replace Nested Conditional with Guard Clauses（ガード節による入れ子の条件記述の置き換え）

- **目的**: 特殊ケースの条件を早期リターンで処理
- **適用シナリオ**: 深い入れ子の条件があり、通常フローが不明確な場合
- **手順**:
  1. 特殊ケースをガード節として先頭に配置
  2. 各ガード節で早期リターンまたは例外を投げる
  3. すべてのガード節後にメインロジックを配置

### Replace Conditional with Polymorphism（ポリモーフィズムによる条件記述の置き換え）

- **目的**: 型やプロパティに基づく条件分岐をポリモーフィズムに置き換え
- **適用シナリオ**: 型に基づくswitch文や連続したif-else文がある場合
- **手順**:
  1. 条件の各分岐に対応するサブクラスを作成
  2. 各サブクラスに共通メソッドを作成
  3. 対応する分岐のコードを各メソッドに移動
  4. 条件分岐をメソッド呼び出しに置き換え

### Introduce Special Case（特殊ケースの導入）

- **目的**: null値や特殊ケースのチェックを専用クラスに置き換え
- **適用シナリオ**: null値や特殊値の同じチェックが複数箇所にある場合
- **手順**:
  1. 特殊ケースを表すクラスを作成
  2. 特殊ケースの振る舞いをクラスに実装
  3. 条件チェックを削除し、特殊ケースオブジェクトを使用

### Introduce Assertion（表明の導入）

- **目的**: コードの前提条件を明示的なアサーションで表現
- **適用シナリオ**: コードが正しく動作するために特定の条件が真である必要がある場合
- **手順**:
  1. 前提条件を特定
  2. アサーションを追加
  3. テストを実行してアサーションが適切であることを確認

## Chapter 11: APIのリファクタリング

### Separate Query from Modifier（問い合わせと更新の分離）

- **目的**: 値を返しつつ副作用も持つ関数を、純粋なクエリ関数と副作用のみのモディファイア関数に分離する
- **適用シナリオ**: 関数が値の計算と状態変更を同時に行っており、副作用なしに値だけ取得したい場合がある場合
- **手順**:
  1. 値を返す純粋なクエリ関数を作成
  2. 副作用のみを行うモディファイア関数を作成（戻り値なし）
  3. 元の関数の呼び出し箇所を、クエリとモディファイアの組み合わせに置換
  4. 元の関数を削除
  5. テストを実行

### Parameterize Function（関数のパラメータ化）

- **目的**: リテラル値のみが異なる複数の類似関数を、その値をパラメータとして受け取る1つの関数に統合する
- **適用シナリオ**: `tenPercentRaise()`と`fivePercentRaise()`のように、定数値だけが異なる関数が複数ある場合
- **手順**:
  1. 類似関数の1つをベースとして選択
  2. 異なるリテラル値をパラメータとして追加
  3. 関数本体をパラメータを使用するよう変更
  4. 他の類似関数の呼び出し箇所をパラメータ化した関数の呼び出しに置換
  5. 不要になった関数を削除
  6. テストを実行

### Remove Flag Argument（フラグ引数の削除）

- **目的**: フラグパラメータで大きく異なるコードパスを切り替える関数を、目的ごとの明示的な関数に分割する
- **適用シナリオ**: booleanや列挙型の引数によって関数内の処理が大きく分岐し、呼び出し側で`true`/`false`の意味が不明瞭な場合
- **手順**:
  1. フラグの各値に対応する明示的な名前の関数を作成
  2. 該当する分岐のコードを各関数にコピー
  3. 呼び出し箇所を適切な明示的関数に置換
  4. 元のフラグ付き関数を削除
  5. テストを実行

### Preserve Whole Object（オブジェクトそのものの受け渡し）

- **目的**: オブジェクトから複数の値を取り出して個別に渡す代わりに、オブジェクト自体を引数として渡す
- **適用シナリオ**: 同一オブジェクトから複数のフィールドを抽出して別の関数に渡している場合
- **手順**:
  1. オブジェクト全体を受け取る新しいパラメータを追加
  2. 関数内部でオブジェクトから必要な値を取得するよう変更
  3. 個別のパラメータを削除
  4. 呼び出し箇所をオブジェクト渡しに変更
  5. テストを実行

### Replace Parameter with Query（パラメータのクエリへの置換）

- **目的**: 関数内部で導出可能なパラメータを削除し、関数シグネチャを簡素化する
- **適用シナリオ**: パラメータの値が他の引数や利用可能な状態から常に導出可能で、呼び出し側が計算してから渡している場合。Replace Query with Parameterの逆操作
- **手順**:
  1. 関数内でパラメータの値を導出する処理を追加
  2. Change Function Declarationでパラメータを削除
  3. 呼び出し箇所から該当する引数を削除
  4. テストを実行

### Replace Query with Parameter（クエリのパラメータへの置換）

- **目的**: 関数内部で行っているクエリ（グローバル参照やコンテキスト依存の取得）をパラメータに置き換え、依存関係を明示化する
- **適用シナリオ**: 関数がグローバル変数や外部コンテキストに暗黙的に依存しており、テスタビリティや再利用性を向上させたい場合。Replace Parameter with Queryの逆操作
- **手順**:
  1. 内部クエリの呼び出しをExtract Variableで変数に抽出
  2. Change Function Declarationでその変数をパラメータとして追加
  3. 呼び出し箇所でクエリを実行し、結果を引数として渡す
  4. 関数内の元のクエリ呼び出しを削除
  5. テストを実行

### Remove Setting Method（setterの削除）

- **目的**: オブジェクト生成時にのみ設定されるべきフィールドのsetterを削除し、不変性を明示する
- **適用シナリオ**: フィールドが生成後に変更されるべきでない場合。setterの存在が誤った変更を招くリスクがある場合
- **手順**:
  1. コンストラクタ内でsetter経由の代入を直接代入に変更
  2. フィールドを`readonly`/`final`等でマーク
  3. setterメソッドを削除
  4. 呼び出し箇所を生成時の値指定に変更
  5. テストを実行

### Replace Constructor with Factory Function（コンストラクタのファクトリ関数への置換）

- **目的**: コンストラクタの呼び出しを名前付きファクトリ関数でラップし、生成の柔軟性と意図の明確さを向上させる
- **適用シナリオ**: コンストラクタの制約（固定の戻り値型、`new`の強制）が不便な場合。サブクラスの返却や意図を伝える名前が必要な場合
- **手順**:
  1. 説明的な名前のファクトリ関数を作成
  2. ファクトリ関数内で`new`を呼び出す
  3. コンストラクタの直接呼び出しをファクトリ関数に置換
  4. 必要に応じてコンストラクタの可視性を制限
  5. テストを実行

### Replace Function with Command（関数のCommandオブジェクトへの置換）

- **目的**: 複雑な関数をCommandオブジェクト（`execute`メソッドを持つクラス）にカプセル化し、分解やライフサイクル管理を容易にする
- **適用シナリオ**: 関数がローカル変数を多く持ちExtract Functionが困難な場合。undo/redo、キューイング、ロギングが必要な場合。Replace Command with Functionの逆操作
- **手順**:
  1. 関数の目的に基づいた名前のクラスを作成
  2. 関数のパラメータをコンストラクタで受け取りフィールドに格納
  3. 関数本体を`execute()`メソッドに移動
  4. プライベートヘルパーメソッドで`execute()`を分解
  5. 呼び出し箇所をインスタンス化と`execute()`呼び出しに変更
  6. テストを実行

### Replace Command with Function（Commandの関数への置換）

- **目的**: 過剰なCommandオブジェクトを単純な関数に戻し、不要な複雑性を除去する
- **適用シナリオ**: Commandクラスが最小限の状態しか持たず、`execute()`が単純な場合。Replace Function with Commandの逆操作
- **手順**:
  1. コンストラクタの引数と同じパラメータを持つ関数を作成
  2. `execute()`のロジックを関数本体にコピー
  3. コマンドのインスタンス化と実行を関数呼び出しに置換
  4. コマンドクラスを削除
  5. テストを実行

## Chapter 12: 継承の扱い

### Pull Up Method（メソッドの引き上げ）

- **目的**: 複数のサブクラスに重複するメソッドを親クラスに引き上げる
- **適用シナリオ**: 2つ以上のサブクラスが同一（またはほぼ同一）のメソッドを持っている場合
- **手順**:
  1. メソッドが全サブクラスで同等であることを確認（異なる場合は先にParameterize Function等で統一）
  2. メソッド内で呼び出される関数が親クラスから利用可能か確認
  3. 親クラスにメソッドを追加
  4. 各サブクラスからメソッドを削除
  5. テストを実行

### Pull Up Field（フィールドの引き上げ）

- **目的**: 複数のサブクラスに重複するフィールドを親クラスに引き上げる
- **適用シナリオ**: 2つ以上のサブクラスが同じフィールドを独立に宣言している場合
- **手順**:
  1. 各サブクラスでのフィールドの使用方法が同等であることを確認
  2. 親クラスにフィールドを宣言
  3. 各サブクラスのフィールド宣言を削除
  4. テストを実行

### Pull Up Constructor Body（コンストラクタ本体の引き上げ）

- **目的**: サブクラスのコンストラクタに重複する初期化ロジックを親クラスのコンストラクタに集約する
- **適用シナリオ**: サブクラスのコンストラクタが同一のセットアップ処理（フィールド代入、バリデーション等）を繰り返している場合
- **手順**:
  1. コンストラクタ間の共通初期化コードを特定
  2. 親クラスのコンストラクタに共通パラメータと共通ロジックを配置
  3. 各サブクラスのコンストラクタを`super()`呼び出しに変更
  4. サブクラスから重複コードを削除
  5. テストを実行

### Push Down Method（メソッドの押し下げ）

- **目的**: 一部のサブクラスでしか使われないメソッドを親クラスからそのサブクラスへ移動する
- **適用シナリオ**: 親クラスのメソッドが特定のサブクラスにのみ関連する場合。Pull Up Methodの逆操作
- **手順**:
  1. メソッドを必要な各サブクラスにコピー
  2. 親クラスからメソッドを削除
  3. テストを実行

### Push Down Field（フィールドの押し下げ）

- **目的**: 一部のサブクラスでしか使われないフィールドを親クラスからそのサブクラスへ移動する
- **適用シナリオ**: 親クラスのフィールドが特定のサブクラスにのみ関連する場合。Pull Up Fieldの逆操作
- **手順**:
  1. 必要な各サブクラスにフィールドを宣言
  2. 初期化処理をサブクラスに移動
  3. 親クラスからフィールドを削除
  4. テストを実行

### Replace Type Code with Subclasses（型コードのサブクラスへの置換）

- **目的**: 振る舞いを分岐させる型コードフィールド（string/integer）をサブクラス階層に置き換え、ポリモーフィズムを活用する
- **適用シナリオ**: 型フィールドに基づくswitch/if-else文が複数のメソッドに散在している場合
- **手順**:
  1. 型コードフィールドをカプセル化（getter作成）
  2. 各型コード値に対応するサブクラスを作成
  3. コンストラクタをファクトリメソッド/関数に置き換え、適切なサブクラスをインスタンス化
  4. 型固有のロジックを各サブクラスのメソッドに移動
  5. 型コードフィールドと条件分岐を削除
  6. テストを実行

### Remove Subclass（サブクラスの削除）

- **目的**: 定数値の返却程度の差異しかないサブクラスを削除し、親クラスのフィールドに統合する
- **適用シナリオ**: サブクラスが意味のある振る舞いの違いを持たず、型コード的な差異しかない場合。Replace Type Code with Subclassesの逆操作
- **手順**:
  1. ファクトリ関数がない場合はReplace Constructor with Factory Functionを適用
  2. 親クラスに差異を表すフィールドを追加
  3. サブクラスのオーバーライドメソッドをフィールド値の返却に変更
  4. ファクトリをフィールド値の設定に変更しサブクラスのインスタンス化を停止
  5. サブクラスを削除
  6. テストを実行

### Extract Superclass（スーパークラスの抽出）

- **目的**: 共通のフィールドやメソッドを持つ複数のクラスに対して、新しい親クラスを作成し重複を排除する
- **適用シナリオ**: 2つ以上のクラスが類似したフィールドやメソッドを持ち、共通の親が存在しない場合
- **手順**:
  1. 新しい空のスーパークラスを作成
  2. 既存クラスを新しいスーパークラスのサブクラスにする
  3. Pull Up Fieldで共有フィールドを引き上げ
  4. Pull Up Methodで共有メソッドを引き上げ
  5. テストを実行

### Collapse Hierarchy（階層の統合）

- **目的**: 差がなくなった親クラスとサブクラスを1つのクラスに統合する
- **適用シナリオ**: サブクラスが親クラスとほぼ同一になり、階層の維持が不要な場合
- **手順**:
  1. 残すクラスを選択（変更が容易な方）
  2. 削除するクラスの全フィールドとメソッドを残すクラスに移動（Pull Up/Push Down）
  3. 削除するクラスへのすべての参照を残すクラスに変更
  4. 空になったクラスを削除
  5. テストを実行

### Replace Subclass with Delegate（サブクラスの委譲への置換）

- **目的**: 継承による振る舞いの変化をコンポジション（委譲）に置き換え、柔軟性を向上させる
- **適用シナリオ**: サブクラスの振る舞いが条件的（一部のインスタンスのみ必要）な場合。複数の独立した変化軸を組み合わせる必要がある場合（単一継承の制約）。実行時に振る舞いを変更したい場合
- **手順**:
  1. サブクラスの特殊な振る舞いを含むデリゲートクラスを作成
  2. 親クラスにオプショナルなデリゲートフィールドを追加
  3. 親クラスの該当メソッドでデリゲートが存在すればデリゲートに委譲するよう変更
  4. サブクラスのインスタンス化を親クラス+デリゲートの設定に置換
  5. サブクラスを削除
  6. テストを実行

### Replace Superclass with Delegate（スーパークラスの委譲への置換）

- **目的**: 不適切な継承関係（"is-a"が成立しない）をコンポジションに置き換え、インターフェースの汚染を防ぐ
- **適用シナリオ**: 親クラスのインターフェースの一部しか使用していない場合。"has-a"や"uses-a"の関係を"is-a"で表現してしまっている場合（例: `Stack extends List`）
- **手順**:
  1. サブクラスに旧親クラスのインスタンスを保持するフィールドを作成
  2. コンストラクタでデリゲートフィールドを初期化
  3. 必要な継承メソッドに対して、デリゲートへの委譲メソッドを明示的に作成
  4. `extends`宣言を削除
  5. 不要なメソッド（親クラスから継承していたが使うべきでないもの）を転送しない
  6. テストを実行
